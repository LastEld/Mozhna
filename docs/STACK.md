# Выбранные языки и стек

Статус: DECIDED — технический выбор исполнителя по прямому поручению владельца от 2026-09-07 переписать проект под облако, разные LLM и ПК/Android/iPhone. Реализация ещё не начата.

## Основной выбор

| Область | Выбор | Причина для MOZHNA |
| --- | --- | --- |
| Адаптивный интерфейс | TypeScript + React + Vite + CSS | Один web-клиент, явные типы, отдельная статическая сборка, простой путь к PWA и Capacitor |
| Сервер и worker | Python + FastAPI + Pydantic | Общая среда для расчётов, извлечения данных, интеграций и LLM adapters; API-схемы из серверных моделей |
| Доступ к данным | SQLAlchemy + Alembic + PostgreSQL | Явные транзакции, миграции и единая долговечная модель данных |
| Очередь первого релиза | PostgreSQL jobs/outbox, Python consumer | Атомарная команда и задание без второго хранилища; короткие транзакции и lease |
| Модели | Собственный тонкий порт ModelProvider + SDK/API adapters | Разные API и capabilities остаются у адаптеров; финансовая логика независима |
| Контракты | Pydantic → OpenAPI/JSON Schema → generated TypeScript client | Один источник схем; клиентские типы не копируются вручную |
| Runtime | Docker backend image; API, worker, scheduler как разные процессы | Один код, независимый перезапуск и масштабирование |
| Файлы | S3-compatible private buckets | Файлы переживают замену контейнера |
| Проверки | pytest для backend; Vitest для UI-логики; Playwright для web paths | Проверяются арифметика, границы и пользовательские сценарии |

FastAPI использует OpenAPI и JSON Schema; это основание для генерации клиентского контракта. Vite предоставляет отдельную сборку frontend. Выбор их сочетания — инженерное решение этого проекта. [FastAPI](https://fastapi.tiangolo.com/features/), [Vite](https://vite.dev/guide/).

## Почему эта комбинация

TypeScript нужен в браузере и для общего UI на устройствах. Python выбран для backend, поскольку финансовая логика невелика по CPU, а основная работа — I/O, данные и интеграции с моделями. SQL сохраняет инварианты и состояние между запусками. Цена двух языков — дисциплина генерируемого API-контракта и две цепочки зависимостей; это учтено в CI.

| Альтернатива | Когда была бы уместна | Почему не основной выбор сейчас |
| --- | --- | --- |
| TypeScript на всех слоях | Команда исключительно JS/TS, простые integrations | Здесь Python удобен для обработки данных и доменных/модельных adapters; единый язык не устраняет границу API |
| Go или Rust backend | Измеренная потребность в низкой latency/CPU/memory | Пока нет такого ограничения, добавится стоимость разработки интеграций |
| Flutter/Dart | Native UI как основной продукт с первого дня | Сначала нужен web-доступ с ПК и мобильных устройств через общий клиент |
| Отдельные Kotlin/Swift приложения | Глубокие платформенные функции | Дублируют клиент до проверки необходимости native возможностей |
| Next.js как full-stack backend | SSR/SEO или серверные React-страницы — существенная часть продукта | MOZHNA — авторизованное приложение с самостоятельным Python API; Vite достаточно |

Capacitor выбран как будущая упаковка того же web-клиента для native Android/iOS, если нужен App Store/Google Play или конкретный native API. Для plugin-specific кода могут потребоваться Swift/Kotlin; они не являются основными языками MOZHNA. [Capacitor](https://capacitorjs.com/docs).

## Зависимости и версии

Python поддерживаемой стабильной версии; TypeScript strict; поддерживаемый Node LTS только для сборки/инструментов. При C0 выбрать конкретные совместимые версии, закрепить их в runtime config, `uv.lock` и `pnpm-lock.yaml`. Backend dependency manager — uv, frontend — pnpm. Не писать фиктивные lockfiles без установки.

Не вводить Celery/Redis, Kubernetes, vector DB или универсальный agent framework до измеренного ограничения. При росте очереди интерфейс JobStore позволит сменить транспорт, сохранив action policy и audit. Выбор модели не требует смены backend-языка.
