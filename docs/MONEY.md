# Денежный контракт

Статус: ядро `mozhna.money.v1` реализовано по выбранной alpha-policy [ADR-0002](adr/0002-money-policy.md). Горизонт 1–366 дней, default 30; даты UTC, один общий EUR-остаток; freshness 24 часа. Это ручной ввод, автоматической банковской сверки нет. Все суммы — целые minor units с currency; binary floating-point для денег не используется.

## Облачный и клиентский контракт

Money Kernel выполняется в Python backend; UI и разные LLM получают один серверный результат. На JSON-проводе integer minor units ограничены диапазоном ±(2^53−1); Pydantic и клиент отвергают выход за диапазон, не округляют. Currency и policy_version обязательны. Финансовые суммы не пересчитываются другим алгоритмом в браузере или модели.

## Термины

| Термин | Смысл |
| --- | --- |
| own_liquid_now | Собственные ликвидные средства по согласованным snapshots; без кредитного лимита |
| available balance | Остаток провайдера с его семантикой holds; не автоматически own_liquid_now |
| essential_limit | Предел, сохраняющий обязательства и резерв в горизонте |
| planned_limit | Предел, сохраняющий также принятые взносы в цель |
| free_now | Показываемый planned_limit с явным горизонтом и допущениями |
| income_gap | Повторяющийся разрыв доходов/расходов; отличается от ближайшей нехватки по датам |

## Реализованная формула

Для каждого момента t, включая сейчас, события и конец горизонта:

```text
cash(t) = own_liquid_now
        + eligible_income(until t)
        - unsettled_commitments(until t)
        - remaining_living_budget(until t)
essential_headroom(t) = cash(t) - reserve_floor(t)
planned_headroom(t) = essential_headroom(t) - goal_allocations(until t)
essential_limit = max(0, min essential_headroom(t))
planned_limit = max(0, min planned_headroom(t))
```

Кандидатная трата вычитается один раз с её даты. Решение вычисляется по **необрезанным** headroom после траты: если исходный дефицит скрыт clamp до нуля, нулевая покупка всё равно не становится CAN.

| Условие после покупки | Решение |
| --- | --- |
| Существенные данные stale, отсутствуют или конфликтуют | `UNKNOWN` / `НЕВІДОМО` |
| Минимальный essential headroom отрицателен | `CANNOT` / `ЩЕ НІ` |
| Essential неотрицателен, planned отрицателен | `CAN_WITH_TRADEOFF` / `МОЖНА, АЛЕ…` |
| Оба неотрицательны | `CAN` / `МОЖНА` |

Режим без будущего дохода и условный календарный прогноз явно различаются. Будущий график поступлений не меняет наблюдаемый остаток. Неопределённый доход не используется для уверенного разрешения.

## Требования будущей сверки и текущие ограничения

- Snapshot не складывается со всей исторической лентой; учитываются лишь события за известной границей покрытия.
- Pending, уже учтённый в available, не вычитается повторно.
- Чек обогащает существующую покупку. Ручная запись и пришедший платёж связываются.
- Перевод между собственными счетами не является доходом или расходом.
- Оплаченная часть обычного бюджета уменьшает его оставшуюся часть.
- Потенциальная экономия и оффер не являются полученными деньгами.
- Разные валюты не суммируются без явной FX-политики; pilot использует одну валюту.
- Горизонт и обязательства за его границей видны; общий остаток не скрывает нехватку на счёте списания.

В alpha журнал/CSV не меняют snapshot. Per-account coverage и сопоставление pending/receipt/bank ещё не реализованы; общий остаток не доказывает возможность списания с нужного счёта.

## Ответ расчёта

Обязательные поля: calculation_id, snapshot_version/hash, policy_version, as_of, horizon_end, currency, basis, assumptions, missing_inputs, planned_limit_minor, essential_limit_minor, decision, affected_commitments, explanation_factors.

Срок задержки цели не выдумывается: без достаточного графика накоплений он неизвестен. Для UNKNOWN зависимые суммы могут отсутствовать; старое число не показывается как актуальное.

## Контрольный пример

Синтетический сценарий: €1 000 средств, €600 аренды, €100 оставшейся жизни, €200 резерва, €50 цели, без доходов. Planned limit €50, essential limit €100. Покупки €40 / €70 / €120 дают CAN / CAN_WITH_TRADEOFF / CANNOT.

Пример и дополнительные границы проверены в [test_money.py](../services/backend/tests/test_money.py). [money-cases.json](../tests/fixtures/money-cases.json) сохраняет синтетические acceptance data. Порядок событий и ограничения определены в ADR-0002.
