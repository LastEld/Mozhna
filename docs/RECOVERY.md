# Backup, восстановление и карантин alpha

Процедура предназначена оператору однопользовательской alpha. Код карантина — [recovery.py](../services/backend/mozhna/recovery.py), синтетические проверки — [test_recovery.py](../services/backend/tests/test_recovery.py). SQLite-тест и реальный PostgreSQL dump/restore с карантином прошли Runtime CI на commit `f6993d5cb933bfa7c3b85a28118e0beca83fb5c8`. Облачный restore drill не выполнен.

## Что сохраняется и что отзывается

| Состояние восстановленной БД | Действие `mozhna.recovery` |
| --- | --- |
| Snapshot, планы, наблюдения и журнал (`records`) | Сохраняются без изменений |
| Jobs со статусом `queued` или `running` | `canceled`, lease очищается, версия увеличивается, причина `RESTORE_QUARANTINED` |
| Завершённые, failed и уже canceled jobs | Сохраняются |
| Все расписания | Удаляются; при необходимости создаются заново после сверки |
| Все серверные сессии | Удаляются; нужен новый вход |
| `owner_state` | Сохраняется, включая ограничение неудачных входов |
| Пароль, MCP bearer и provider keys в окружении | Не меняются; ротация выполняется отдельно |

Команда работает в одной транзакции и допускает повторный запуск: после первого карантина счётчики повторного запуска равны нулю. Она **не останавливает процессы сама**. Флаг `--runtime-stopped` — подтверждение оператора, а не техническая блокировка API/worker/scheduler. Если хотя бы один процесс продолжает работать, использовать эту процедуру как защиту от повторного исполнения нельзя.

## 1. Подготовить backup и остановить выполнение

Сохраните commit/image и Alembic revision вместе с датой backup. Ограничьте доступ к архиву: он содержит финансовые записи и может содержать сессии. Не помещайте его в репозиторий или GitHub artifact. Пароли задавайте менеджером секретов или защищённым `.pgpass`, а не аргументами команды.

Остановите **все API, worker и scheduler**, включая другие replicas и временные экземпляры. Для локального Compose из корня проекта:

```bash
docker compose stop api worker scheduler
```

На Render остановите соответствующие сервисы в Dashboard и дождитесь завершения. Убедитесь, что нет оставшегося worker: SIGTERM даёт ему закончить текущую job; принудительное завершение может оставить `running` lease. Не включайте автоматический deploy или restart на время восстановления.

Для PostgreSQL backup используйте установленный `pg_dump` совместимой версии. Следующая команда использует исходную БД и пользователя из заранее настроенных `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE` и защищённой аутентификации:

```bash
pg_dump --format=custom --file=/secure-backups/mozhna-before-restore.dump
```

Путь `/secure-backups` обозначает заранее созданное защищённое место, не папку репозитория. Для managed PostgreSQL можно взять backup средствами провайдера; его наличие само по себе не подтверждает восстановимость.

## 2. Восстановить отдельно

Сначала восстановите в **новую пустую БД**, сохранив исходную. Для PostgreSQL, где оператор имеет права `createdb` и подключение через те же параметры окружения:

```bash
createdb mozhna_restore_review
pg_restore --dbname=mozhna_restore_review --no-owner /secure-backups/mozhna-before-restore.dump
```

Если имя уже занято, выберите другое новое имя; не очищайте существующую БД ради этой инструкции. На managed hosting используйте предусмотренное провайдером создание восстановленной БД. Не запускайте приложение против неё до карантина.

Настройте `DATABASE_URL` операторской backend-сессии на **восстановленную**, а не исходную БД. Значение должно включать правильный SQLAlchemy driver, например схему `postgresql+psycopg`; URL и пароль в отчёт не копируйте. Проверьте endpoint и имя базы в закрытой конфигурации. Для чтения локального `.env` используйте собственный менеджер окружения: Python-приложение не загружает корневой `.env` автоматически.

Из `services/backend`, кодом выбранного release:

```bash
uv run alembic current
uv run alembic upgrade head
uv run python -m mozhna.recovery --runtime-stopped
```

Ожидается JSON со счётчиками `quarantined_jobs`, `removed_schedules`, `revoked_sessions`. При ошибке migration или карантина оставьте runtime остановленным и разберите причину. Не заменяйте её запуском API, который автоматически обработает восстановленную очередь.

## 3. Проверить и возобновить

1. Проверьте, что queued/running jobs, schedules и sessions отсутствуют; повторный карантин должен вернуть нули. Сверьте количество финансовых records с backup и сохранность синтетического контрольного snapshot при учебной проверке.
2. Переведите конфигурацию всех процессов на выбранную восстановленную БД, сохраняя worker/scheduler остановленными. Если инцидент затрагивал секреты, отдельно смените пароль, MCP bearer и затронутые provider keys. Карантин не отзывает static MCP bearer.
3. Запустите только API. В production `/healthz` должен вернуть 200 после проверки таблиц/столбцов и актуальной Alembic migration. Выполните новый вход: старая cookie должна быть недействительна.
4. Перед любым финансовым решением вручную сверьте восстановленный остаток, обязательства, планы и журнал с текущими фактическими данными и обновите snapshot/as_of. Это обязательно даже для backup моложе 24 часов: после его создания могли произойти операции. Карантин сохраняет прежние records и не делает их актуальными. Не создавайте платные задания во время сверки.
5. Запустите worker/scheduler и убедитесь, что старые queued/running jobs остаются canceled, а старые расписания не появились. Расписания и нужные задания создавайте заново только после проверки данных. Для smoke достаточно бесплатного сравнения.
6. Зафиксируйте commit, revision, дату backup, длительность восстановления, счётчики карантина и результат smoke без финансового содержимого или секретов. Это доказательство конкретного drill, а не обещание заданных RPO/RTO.

Карантин не отменяет уже отправленный модели HTTP-запрос и не удаляет сохранённое провайдером содержимое. Он не восстанавливает банковскую сверку и не повторяет внешние отправки: таких handlers в alpha пока нет. Будущие approvals/мандаты потребуют отдельной политики восстановления до их реализации.
