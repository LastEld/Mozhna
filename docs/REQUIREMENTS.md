# Требования и приёмка

Все строки ниже — требования, не отчёт о реализации.

| ID | Возможность | Проверяемый результат |
| --- | --- | --- |
| FIN-01 | Ручное состояние | Остаток, обязательства, резерв и цель сохраняются с владельцем и версией |
| FIN-02 | Проверка покупки | Один snapshot и policy дают одинаковые числа и статус без модели/сети |
| FIN-03 | Неполные данные | Stale/конфликтующий остаток даёт UNKNOWN с причиной |
| FIN-04 | Учёт источников | Повторный импорт, pending/booked, чек и перевод не удваивают деньги |
| FIN-05 | Прогноз | Будущий доход, наблюдаемый баланс и сценарий явно различимы |
| RED-01 | Повторяющаяся потребность | Текущий способ и ограничения подтверждены пользователем |
| RED-02 | Альтернатива | Стоимость сравнивается на одинаковый объём/период; видны затраты запуска |
| RED-03 | Микроконтракт | Есть baseline, выбранное изменение, правило проверки и остановки |
| RED-04 | Результат | Прогноз, реальные расходы, остатки запасов и субъективная полезность разделены |
| EARN-01 | Дефицит | Ближайшая нехватка по датам отделена от устойчивого income gap |
| EARN-02 | Поиск | Результаты имеют источник, время проверки, фильтры и причины соответствия |
| EARN-03 | Черновик | Каждое существенное утверждение связано с подтверждённым фактом профиля |
| EARN-04 | Отправка | Конкретный payload одобрен, результат подтверждён либо OUTCOME_UNKNOWN |
| INT-01 | Банк | Один read-only adapter с воспроизводимой сверкой и видимой freshness |
| INT-02 | Чеки | Извлечение создаёт предложение; связь с платежом исключает двойную трату |
| INT-03 | Telegram | Проверены user/chat/account; упоминание не выдаёт полномочия |
| INT-04 | MCP | Те же application services и проверки владельца, что у UI/API |
| TRUST-01 | Приватность | Экспорт/удаление, минимальные scopes и отсутствие секретов в модели/logs |
| TRUST-02 | Отзыв | Неотправленные действия блокируются после отзыва; in-flight исход выясняется |
| OPS-01 | Восстановление | Backup восстанавливает состояние без повторной отправки и оживления отозванных прав |
| CLOUD-01 | Durable execution | После принятия job закрытие клиента/restart worker не теряют команду |
| CLOUD-02 | Расписания | Cloud scheduler соблюдает timezone и не дублирует due run |
| CLOUD-03 | Продолжение | Другое устройство получает тот же plan/job version; stale write отвергается |
| MODEL-01 | Сменные LLM | Один domain contract проходит через два реальных provider adapters |
| MODEL-02 | Capability/budget policy | Недоступная capability и исчерпанный бюджет дают явный статус без скрытого fallback |
| DEVICE-01 | Адаптивный UI | ПК/Android/iPhone/tablet имеют проверенные layout и основные действия |
| DEVICE-02 | Progressive enhancement | Отсутствие push/install/SSE не блокирует базовые сценарии |
| DEVICE-03 | Offline boundary | Stale данные помечены; approval и каноническая запись требуют актуального cloud state |

Реализация указывает эти ID в issue/PR и добавляет доказательство только для затронутых возможностей.
